# 体彩优先预测上下文设计

## 背景

当前系统已经接入 Sporttery/体彩公开接口，并能在存在 `fixture_sporttery_mappings` 映射时刷新 `sporttery` 上下文。实际验证结果显示：

- 体彩开关已启用。
- 赛程有 72 场。
- 体彩公开接口当前返回 5 天、22 场。
- 当前数据库只有 1 条体彩映射。
- 已有映射的比赛刷新 `sporttery` 成功。
- 没有映射的比赛刷新时 `sporttery` 为 `not_requested`。

因此问题不是体彩接口整体不可用，而是映射补齐和 UI 数据源边界不清晰。

用户确认采用方案 C：预测上下文彻底转为体彩数据，API-Football 只保留赛程、比分、状态和球队基础信息。

## 目标

把预测上下文收敛为体彩数据源。

成功标准：

- 打开数据卡时，系统自动尝试补齐当前比赛体彩映射并刷新体彩数据。
- 用户请求预测时，系统默认只刷新体彩上下文，不再刷新 API-Football 的赔率、历史交锋、球员阵容伤停。
- 数据卡不再展示 API-Football 旧的 `odds`、`head_to_head`、`squad` 结果。
- UI 文案从“赔率”改为“官方指数”或“市场背景”，弱化权重暗示。
- 后台提供一键同步体彩映射入口，展示映射数量和同步反馈。
- 赛程卡顶层展示最新预测摘要，不要求用户先进入历史记录或二级卡片才能看到模型 PK 结果。
- 全仓测试、类型检查和 lint 通过。

## 非目标

本次不做：

- 手工映射的复杂可视化编辑器。
- 非世界杯比赛的展示。
- 将官方指数作为胜平负预测权重。
- 改排行榜计分规则。
- 删除 API-Football 赛程同步能力。
- 删除已存在的数据库表；旧表可保留但不再作为默认预测上下文来源。

## 数据源边界

API-Football 保留职责：

- 赛程导入。
- 比赛状态同步。
- 比分同步。
- 球队原始名称、logo、fixture id。

体彩承担预测上下文：

- 官方胜平负或让球官方指数。
- 历史交锋。
- 积分榜。
- 近期战绩。
- 特征胜率。
- 伤停明细。

默认数据选项：

- `useSporttery: true`
- `useOdds: false`
- `useHeadToHead: false`
- `usePlayerLineupInjuries: false`
- `useApiFootballPrediction: false`
- `useDongqiudiIntel: false`

说明：`useDongqiudiIntel` 在本次默认预测上下文中关闭，避免与“体彩作为唯一预测上下文”的产品口径冲突。已有懂球帝代码可保留，不作为默认预测数据注入。

## 自动映射

新增后端能力：按单场比赛自动确保体彩映射。

输入：

- API-Football fixture id。
- 主队中文名。
- 客队中文名。

流程：

1. 查询 `fixture_sporttery_mappings`。
2. 如果已存在，直接返回该映射。
3. 如果不存在，调用体彩全赛程接口。
4. 只在 `leagueAbbName` 或 `leagueAllName` 为 `世界杯` 的体彩比赛中查找。
5. 用中文主客队精确匹配。
6. 匹配成功后写入 `fixture_sporttery_mappings`。
7. 匹配失败时返回空结果，不阻断数据卡和预测请求。

匹配规则必须使用代码中明确字段：

- API-Football 侧：`home_team_name`、`away_team_name` 当前保存的是中文展示名。
- 体彩侧：`homeTeamAbbName`、`awayTeamAbbName`。

队名简称差异暂不做模糊匹配；后台一键同步会展示匹配数量，后续再补手工映射 UI。

## Context Refresh

`refreshFixtureContext` 保留多域能力，但默认调用方只请求体彩域。

打开数据卡：

1. 后端收到 refresh 请求。
2. 如果 `useSporttery` 为 true 且体彩开关启用，先自动确保当前比赛体彩映射。
3. 有映射则拉取体彩六类数据并保存 `sporttery` snapshot。
4. 没有映射则返回 `sporttery` 的 `unavailable`，摘要为 `体彩暂未覆盖该场比赛`。

预测请求：

1. 默认请求只带体彩数据选项。
2. 如果用户在预测配置中关闭体彩数据，则不会刷新任何预测上下文。
3. 如果体彩刷新失败，预测仍可继续，但上下文会明确标记失败或不可用。

## 摘要结构

体彩摘要从单段长文本优化为分区摘要。共享 DTO 暂不新增复杂结构，仍兼容 `summary: string`，但文本格式统一为可分段解析的纯文本：

- `官方指数：...`
- `历史交锋：...`
- `积分形势：...`
- `近期状态：...`
- `特征对比：...`
- `伤停影响：...`

前端展示时按这些分段拆成情报条目。

官方指数展示要求：

- 不使用“赔率”作为数据卡标题。
- 可在正文中保留接口原始含义，例如“胜平负官方指数”。
- 提示词必须强调：官方指数只作市场背景，不得作为预测权重。

## 前端数据卡

`MatchContextDrawer` 改为“赛前情报”面板。

展示规则：

- 只展示 `sporttery` 域。
- 如果状态是 `cached`，按摘要分段展示：
  - 官方指数
  - 历史交锋
  - 积分形势
  - 近期状态
  - 特征对比
  - 伤停影响
- 如果状态是 `unavailable`，展示覆盖说明。
- 如果状态是 `refresh_failed`，展示失败原因。
- 不再显示 API-Football 的 `odds`、`head_to_head`、`squad` 卡片。

## 预测配置

`PredictionRequestDrawer` 的数据选项区简化：

- 默认只显示“使用体彩赛前情报”。
- 隐藏或移除 API-Football 赔率、历史交锋、球员阵容伤停选项。
- 保留任务类型、提示词模板、自定义提示词、输出风格。

提交 payload 仍使用现有 `PredictionDataOptionsDto`，但默认关闭旧字段。

## 顶层预测摘要

赛程卡顶层显示最新预测摘要。

数据来源：

- 当前会话刚生成的预测结果。
- 或该比赛历史预测接口返回的最近一条 run。

展示字段：

- 综合观点。
- 参考比分。
- 模型投票分布。
- 成功/失败模型数。

交互：

- 点击“历史”仍打开历史预测记录。
- 点击“查看报告”进入模型详细报告。
- 如果没有预测结果，赛程卡不占用大面积空白。

## 后台配置

数据源配置页新增体彩区域：

- 显示体彩开关。
- 显示当前映射数量。
- 提供“一键同步体彩映射”按钮。
- 同步完成后展示匹配数和未匹配数。

后端新增批量同步接口：

- `POST /api/admin/sporttery-mappings/sync`

响应示例：

```json
{
  "matched": 12,
  "unmatched": 10,
  "totalSportteryMatches": 22
}
```

该接口只写入精确匹配的世界杯比赛，不删除已有映射。

## 提示词

内置提示词更新：

- 用“官方指数 / 市场背景”替代面向用户的“赔率驱动”表达。
- 删除旧 API-Football 赔率权重暗示。
- 保留明确约束：官方指数不得作为胜平负预测权重。
- 预测依据优先级写为：球队状态、积分形势、近期战绩、历史交锋、伤停影响、赛程背景。

## 测试

API 测试：

- Sporttery 自动映射成功。
- Sporttery 自动映射失败返回 `unavailable`。
- Context refresh 默认不触发 API-Football 赔率、历史交锋、阵容伤停接口。
- 批量同步映射接口返回匹配数量。
- 预测请求默认保存旧 API-Football 上下文字段为 false，`useSporttery` 为 true。

Web 测试：

- 打开数据卡只请求体彩默认选项。
- 数据卡只展示体彩赛前情报。
- 预测抽屉只展示体彩赛前情报开关。
- 赛程卡展示最近预测摘要。
- 后台数据源配置页展示体彩同步入口。

最终验证：

- `corepack pnpm test`
- `corepack pnpm typecheck`
- `corepack pnpm lint`

## 风险

- 体彩全赛程当前只返回近期比赛，因此远期比赛会显示“体彩暂未覆盖该场比赛”。
- 中文简称差异会导致部分世界杯比赛无法自动映射，例如“沙特”与“沙特阿拉伯”。
- 一键同步只做精确匹配，后续需要手工映射 UI 或别名表提高覆盖率。
- 旧 API-Football 上下文代码保留但默认不用，后续如彻底删除需另起清理任务。
