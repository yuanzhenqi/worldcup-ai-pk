# 预测结果与投注组合 UI 重构设计

## 背景

当前系统已经支持多模型预测、赛果 Agent、单场投注组合 Agent、体彩赛前情报和串关组合后端接口，但用户侧还有几个断点：

- 串关组合按钮在前端固定禁用，用户不知道什么时候可以生成。
- 单场投注方案虽然由模型生成，但赛程卡片上只露出第一条结果，容易误解为单模型方案。
- 预测结果、投注方案、失败日志分散展示，信息层级不够清楚。
- 手机端字体偏大、内容密度偏低，一屏能看到的信息太少。
- 投注方案使用长段文字描述，缺少结构化字段。
- 部分模型调用失败时没有按失败类型清楚呈现。
- 仍存在启用的旧提示词模板使用“赔率变化权重”表达，和当前策略冲突。

本轮目标是把“赛果预测”和“投注组合模拟”融合成清晰的结果卡，同时让串关入口符合用户决策路径。

## 目标

成功标准：

- 用户能一眼看到每场比赛的综合赛果、参考比分、模型成功/失败数和主投注方案。
- 单场投注方案以结构化字段展示，不用大段文字堆叠。
- 串关入口只在已有单场投注方案的比赛上出现，选择 2 场以上后才能生成。
- 桌面端保留模型 PK 表格，手机端改用短指标卡和标签，字体更克制。
- 所有按钮使用统一的尺寸、圆角、颜色、状态和禁用样式。
- GPT/Gemini 等模型失败时，日志和后台测试能区分接口形态、空内容、JSON 解析和 HTTP 错误。
- Agent A 不使用体彩指数作为赛果权重；Agent B 可使用体彩可选项生成投注组合模拟。

## 非目标

- 不接入真实下单。
- 不输出“保证收益”“稳赚”“必中”等表达。
- 不实现复杂资金管理算法。
- 不在本轮替换全部外部数据源。
- 不把串关组合做成自动推荐；仍由用户主动选择比赛。

## 核心信息架构

采用 A+B 融合方向：

- 桌面端使用“单卡融合摘要 + 模型表格”。
- 手机端使用“指标卡 + 标签方案”。
- 详情报告仍在二级弹窗或历史详情中查看。

每场比赛在有预测反馈后展示三层信息：

1. 综合摘要：赛果共识、参考比分、模型成功/失败数。
2. 投注组合摘要：主方案、风险等级、注数、是否已加入串关。
3. 模型明细：每个模型的赛果、比分、信心、主方案、状态。

首页不展示完整长报告。长报告放在“查看报告”或历史详情里。

## 串关入口设计

主入口放在“单场投注方案卡”内，不放在右侧通用操作列。

原因：

- “加入串关”是针对单场投注方案的动作，不是比赛基础动作。
- 用户需要先看到主方案、风险等级和注数，再决定是否加入。
- 没有 `single_combo` 的比赛不应该显示可选入口。
- 手机端如果把它放入 `预测 / 数据 / 历史` 操作列，会导致按钮过多。

桌面端：

- 单场投注方案卡右上角显示按钮。
- 未选状态：`加入串关`
- 已选状态：`已加入`
- 不可选状态不显示按钮，而不是显示禁用按钮。
- 串关工作台位于筛选区下方，展示已选比赛和生成按钮。

手机端：

- 单场投注方案卡底部右侧显示短按钮。
- 未选状态：`加入`
- 已选状态：`已加入`
- 当已选比赛数量大于 0 时，底部或工作台区显示 `已选 N 场`。

生成条件：

- 已选择比赛数不少于 2。
- 每场比赛都有解析成功的 `single_combo`。
- 用户选择风险等级。
- 用户设置注数。

若条件不足：

- 工作台显示缺口，例如 `还需 1 场` 或 `所选比赛缺少单场方案`。
- 生成按钮禁用，并显示具体原因。

## 按钮统一规范

建立一组页面通用按钮样式，避免每个区域自行定义：

- 主按钮：深绿色背景、白字，用于 `预测`、`生成串关组合`、`查看报告` 等主动作。
- 次按钮：浅绿色背景、深绿色字，用于 `数据`、`历史`、`加入串关`。
- 选中按钮：深绿色描边或深绿色背景，文案改为 `已加入`。
- 危险或清除按钮：仅用于移除串关选择，使用低饱和红色或文本按钮。
- 禁用按钮：统一降低透明度，不响应 hover，不改变布局。

尺寸规则：

- 桌面端按钮高度保持稳定，宽度由场景决定但同组按钮等宽。
- 手机端按钮高度不低于可触控尺寸，字体小于当前默认大号按钮文案。
- 图标按钮只用于明确图标语义；本轮不强制引入新图标。

状态规则：

- loading：显示短文案，例如 `请求中`、`生成中`。
- selected：显示 `已加入`，样式要和未选状态明显区分。
- disabled：必须有旁边说明或工作台状态说明，不让用户猜原因。

## 投注方案结构化展示

单场方案摘要不再直接展示长段文本，统一拆成字段：

- 主方案：玩法、选择、风险、注数。
- 备选方案：最多 2 条，每条展示玩法和选择。
- 规避项：展示不建议参与的条件。
- 触发条件：展示方案成立的比赛情境。
- 数据缺口：展示未获取或不完整的数据。

桌面端模型表格列：

- 模型
- 赛果
- 比分
- 信心
- 主方案
- 风险
- 状态

手机端折叠成卡片：

- 第一行：模型名、状态。
- 第二行：赛果、比分、信心。
- 第三行：主方案、风险。

## 多模型方案汇总

当前单场方案数据仍由每个模型独立生成：

- Agent A：同一模型生成赛果分析。
- Agent B：同一模型基于 Agent A 输出生成单场方案。

UI 汇总时不只显示第一条方案，而是生成展示层汇总：

- `主方案共识`：多个模型选择相同或相近方案时显示。
- `分歧方案`：模型方案不一致时列出差异。
- `高风险规避项`：合并模型输出的规避项。
- `模型方案表`：保留逐模型结果，方便查看 PK。

串关组合 P0 仍消费每场最新单场方案。后续可升级为多模型共识串关。

## 模型失败呈现

后端需要保留原始失败信息，并在前端归类展示：

- HTTP 错误：例如 429。
- 返回不是 JSON：例如 `text/event-stream`。
- 内容为空：例如 assistant `content` 为空。
- JSON 解析失败：内容中没有有效对象或字段不符合结构。
- 字段不合法：例如赛果字段不在允许值内。

预测摘要显示：

- `成功 N / 失败 M`
- 失败模型可展开查看原因。

后台模型测试按钮显示三层结果：

1. 接口连接是否成功。
2. assistant 内容是否非空。
3. JSON 预测输出是否可解析。

## 提示词与数据注入

Agent A：

- 只做足球赛果、比分、关键因素和风险判断。
- 体彩指数只能作为市场背景，不作为赛果权重。
- 使用历史交锋、积分形势、近期状态、特征对比、伤停等上下文。
- 对缺失数据必须写明。

Agent B：

- 消费 Agent A 的结构化输出。
- 使用体彩可选玩法和选项生成投注组合模拟。
- 输出结构化字段，不输出大段无结构文本。
- 不重新预测赛果，不覆盖 Agent A 结论。

本轮需要修正旧提示词模板：

- 禁用或改写仍包含“赔率变化权重”的旧模板。
- 内置模板统一使用“体彩选项”“投注组合模拟”“风险方案”等表达。
- 不使用“赔率作为赛果预测权重”的表达。

## 响应式设计

桌面端：

- 赛程卡片保留横向扫描路径。
- 预测反馈区跨列展示，综合摘要在上，模型表格在下。
- 单场投注方案卡位于综合摘要旁或下方，保持紧凑。

手机端：

- 比赛基础信息、综合预测、投注方案分块显示。
- 字体下调，避免标题级字号用于卡片内部字段。
- 模型明细默认折叠或以紧凑卡片展示。
- 串关入口使用短文案 `加入`，不占满整行。
- 不出现横向滚动。

## 测试计划

前端测试：

- 预测反馈出现后展示综合摘要。
- 有单场方案时显示加入串关入口。
- 没有单场方案时不显示加入串关入口。
- 选择 2 场后生成串关按钮启用。
- 未满足条件时按钮禁用并显示原因。
- 模型失败原因能在摘要中展开查看。
- 手机端布局不出现横向滚动。

后端测试：

- `createParlayCombinationRun` 保持至少 2 场校验。
- 单场方案缺失时返回可读错误。
- GPT 流式响应或非 JSON 响应被归类为接口形态不兼容。
- Gemini 空内容被归类为空内容。
- 旧提示词模板不再包含“赔率变化权重”。

手工验证：

- 在桌面端检查赛程卡片、投注方案、串关工作台。
- 在手机宽度检查字体、按钮、卡片密度。
- 使用最近失败的 Gemini 和 GPT 配置运行模型测试，确认失败原因更清楚。

## 风险

- 当前串关后端只取每场最新单场方案，尚未做多模型共识串关；UI 需要明确这是“基于已选单场方案生成”。
- 部分模型返回格式不稳定，修复客户端后仍可能因为模型输出字段不合法失败。
- 体彩结构化玩法已保存原始数据，但当前提示词仍主要使用摘要；本轮需要把结构化玩法注入 Agent B，避免方案缺少可选项。
